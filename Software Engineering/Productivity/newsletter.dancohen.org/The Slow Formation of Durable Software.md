# [The Slow Formation of Durable Software](https://newsletter.dancohen.org/archive/the-slow-formation-of-durable-software/)

## [HackerNews Discussion](https://news.ycombinator.com/item?id=49980346)
* [One commenter](https://news.ycombinator.com/item?id=50005411) mentioned that the following quote resonated with them

  > “… we could not have accelerated Zotero’s conception, because we did not know exactly what we wanted, and so could not have written coherent prompts for an LLM.”

  * Commenter argues that a surprising proportion of software products (and maybe even businesses) are solutions in search of a problem
* [Another commenter](https://news.ycombinator.com/item?id=50004901) argues that it is not possible to make anything good quickly
  * [In response](https://news.ycombinator.com/item?id=50005478), a commenter says that "speed" makes you prioritize the tasks that actually matter, so one delivers features that actually count
    * Additionally, sometimes thinking longer about a particular problem doesn't get one closer to the correct answer
      * Can rearrange, refactor, rewrite, redesign, but the output might not be objectively better than what currently exists
    * [Another commenter](https://news.ycombinator.com/item?id=50008511) points out that most software is crap, and without the pressure to ship, smart programmers would keep polishing "the turd" forever
      * This commenter posits that the best, high-quality, slow-developed software isn't the best because programmers knew when to stop - it's because the scope and timeline were bounded upfront.
